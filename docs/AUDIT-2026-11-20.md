# Allurus audit, 2026-11-20

**Repo:** `allurus-hr` at commit `d65057c` (v3.79), live at allurus.my/app. **Mode:** read-only. Nothing was changed, deployed or written to production. No tokens were minted and no customer account was used. Production was read through the owner's service-account key as **counts and settings only**; the only first names used are the ones the brief names (Fouzer, test2).

**How the evidence was gathered:** the repo at `d65057c`; `npm test` (594 pass), `npm run test:rules` (172 pass, run on 2026-11-14 and 2026-11-19); the browser checks `tests-e2e/admin-mobile.e2e.js`, `ui-clip.e2e.js`, `onetap.e2e.js`, `phone-home-attendance.e2e.js`; two ad-hoc scripts for the staff routes and for load time on a throttled phone; read-only queries of the Major Far East company; and the GitHub Actions run for `d65057c`.

**What I could not verify** (so nothing below claims it): the Firebase and Google Cloud consoles (backups, billing, quotas, domains, Auth settings), what is on a real staff phone, and any code that is not in this repo, including the "stock-out" audit that was pasted into this project (section 3.2).

---

## 1. Summary

**Overall: 6.5 / 10.** The core HR phone experience is solid and unusually well tested for a product of this age: the rules engines are pure and unit tested (594 tests), the Firestore rules have 172 emulator tests, every admin route fits a 390 px phone, and the staff phone check-in is now one tap with no silent failures. It is **not ready to be the system of record for payroll at Major Far East yet**, mainly because of configuration and data, not code: the company is set up with the **Kuala Lumpur calendar and Saturday–Sunday weekend although it is in Terengganu**, statutory numbers are mostly empty, and both payroll runs are still drafts. There is **no evidence of a scheduled Firestore backup**, and the only automated gate (CI) runs the unit tests only.

## 4. Cross-cutting findings

### 4.1 Security

- **Collections and rules:** 55 `match` blocks, 164 `allow` lines, in 984 lines. Every collection in the live app has a rule; the default is deny. Client-writable collections are limited to the person's or company's own data. `auditLog`, `generalEntries`, `posIntegrations`, `staffKeys` and the POS tables are not writable from a browser as designed.
- **Collections with no rules test found:** the six `pos_*` collections, `announcements`, `enquiries`, `finderRules`, `demoZones`. (`generalEntries` and `posIntegrations` each appear in one test.)
- **Tenant isolation:** asserted in `billing`, `prod`, `staffkeys` and `stafflinks` rules tests ("another company ... fails"). There is **no single table-driven test** that every collection family refuses a signed-in user of company B. That is the one test I would add first.
- **Client-trusted `company_id`:** none in committed code. The callable functions take `tenantId` from the client but verify that `users/{uid}.tenantId` matches and the user is not disabled (`functions/pos-core.js:16-24`). `receivePosJournal` authenticates by HMAC, then checks the tenant against `posIntegrations`. The `/api/v1` design in the pasted audit (company from the request) would **not** meet this bar and does not exist here.
- **Secrets:** no private key, token or password in the tracked files. The Firebase web key appears in `js/firebase-config.js`, `site/js/config/site.js` and `pos/apps-script-server/Setup.gs` (public by design). `scripts/serviceAccount.json` exists on the owner's machine, is git-ignored and works against production: keep it off shared machines and rotate it if it was ever copied.
- **`npm audit --omit=dev`:** 0 vulnerabilities.
- **Rules size, and how to reduce it (issue 5):**
  1. Measure the real cost per path with the emulator on the largest writes (credit note on a sent invoice with an audit entry; inventory stock-in with many fields); record the number in the rules header.
  2. Compute `bucketClass(b)` once and store it on the document (`r` is already stored); compare `request.resource.data.r == resource.data.r` instead of recomputing the class from the id on every write.
  3. Split the invoice rule by action (`allow create`, `allow update` per status transition) with `request.resource.data.diff(...).affectedKeys().hasOnly([...])` first, so a rejected write stops early.
  4. Move whole-document checks (line items, totals) to a callable function for the rare, expensive actions (void, credit note) and keep the rule as a simple "only the function may do this".
- **Audit log:** see issue 8.

### 4.2 Data safety

Backups: see issue 3. A bad deploy: hosting is a static site deployed with `firebase deploy --only hosting`; the previous release can be rolled back from the Hosting console. A bad rules deploy has no rollback except `docs/rules-backup/` (latest `2026-11-12b`; the rules have changed since): refresh it on every rules deploy. Deploys go to the live project that real customers use; there is no staging project.
