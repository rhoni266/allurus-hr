# Allurus POS

Multi-tenant, offline-first, omnichannel POS for the Malaysian market (F&B, retail, time-based services). Full design: `allurus-pos-architecture.md` (schema, sync strategy, API, roadmap). Read it before changing architecture. Where it differs from the code (it predates the fixes below), the code and this file win.

## Stack

* Backend: Laravel 13 (PHP 8.4 locally; keep code 8.3-compatible), PostgreSQL 17 (row-level security), Redis, Horizon, Sanctum, Reverb, Pest
* Back-office: Vue or React SPA
* Terminal: Flutter or React Native, SQLite (SQLCipher), outbox-based sync

## Non-negotiable rules

1. Money is integer sen. Never floats, never `decimal` math in PHP. Quantities are `qty_milli` (qty x 1000) inside the pricing engine.
2. Every tenant table has `tenant_id` and uses the `BelongsToTenant` trait. The scope fails closed (no tenant context = no rows). Postgres RLS is the second wall (`App\Database\Rls::enable()`, with `FORCE` and `WITH CHECK`). Never take the tenant from a client header.
3. IDs are UUIDs generated by the client (terminals create orders offline). Server never re-keys a synced order.
4. Sales are append-only facts. The server never rewrites a completed sale because a price changed. Flag a `sync_conflicts` row instead. Corrections are new rows (void/refund).
5. Stock moves by deltas written to `stock_movements`. `stock_levels` is a projection. Negative stock is allowed and alerted, never blocks a sale.
6. Sync push is idempotent on `(terminal_id, client_seq)`, and each handler is idempotent on its own domain id too (order / void / payment / adjustment / session id). One DB transaction per mutation. A mutation that fails validation is stored as `rejected` and must not block later ones. `retry` (stores nothing) covers transient DB errors, unexpected server exceptions, and a mutation whose order hasn't synced yet (`DependencyMissing`, e.g. a void on terminal B of terminal A's offline sale), up to 72 h, then `rejected: dependency_missing`. Terminals back off a waiting row on its own (`not_before`) so later rows still go through.
   Offline actions are never refused for *who* did them: a cashier's void, a correction by the wrong role or unknown staff are stored and flagged (`unauthorized_*`, `unknown_staff`).
7. Pricing lives in one place. `app/Billing/PricingEngine.php` is checked against `spec/pricing/vectors.json`. The terminal (Dart/TS) must reproduce the same vectors. To change pricing behaviour: edit the vectors first, bump `SPEC_VERSION`, then update every implementation.
8. Tax rates are data, not code. SST rules are versioned rows (`tax_rules`), synced to terminals, and the `rule_version` is stored on each order. Confirm current SST rates and scope with the Royal Malaysian Customs Department before go-live.
9. Online-only payment methods (FPX, DuitNow QR, GrabPay, TNG) are disabled offline. Offline = cash only.
10. Payment webhooks: verify signature on the raw body, dedupe by gateway event id, ack fast, process on a queue, and reconcile pending payments with a poller.

### Learned the hard way (each found by the chaos simulator; each has a regression test)

* **The change feed is Postgres triggers, not Eloquent events** (`database/migrations/2026_01_01_000060_create_sync_triggers.php`). `increment()`, query-builder updates and raw SQL skip model hooks, and a missed feed row leaves terminals on a stale price forever. Don't reintroduce PHP-side feed writes. `row_version` is bumped by the trigger, so call `->refresh()` if you need it in memory.
* **Timestamps carry offset and microseconds.** Models use `PreciseTimestamps` (`App\Database\Timestamps::FORMAT`); query-builder bindings must pass `->format(Timestamps::FORMAT)` explicitly. DB sessions are pinned to UTC in `config/database.php`. Device-time columns use `timestampTz(..., 6)` — Laravel's default precision is whole seconds.
* **Terminals and `device_pairing_codes` are not tenant-scoped and have no RLS**: both are looked up before a tenant is known (Sanctum auth, device registration). Pairing codes are found only by SHA-256 hash.

### Devices and staff

* Pairing: a one-time code (8 chars, 15 min, single use, stored as a hash) comes from `php artisan pos:pairing-code <tenant-slug> [outlet-id]` or from an owner/manager signed in on a paired terminal (`POST /api/v1/devices/pairing-codes`). The device redeems it at `POST /api/v1/devices/register` (public, rate-limited) for a Sanctum token with **only** `pos:terminal`. Re-pairing the same device revokes its old token and staff sessions.
* Staff sign-in: `POST /api/v1/auth/login {staff_id, pin}` on a paired terminal returns a 12-hour session token, sent as `X-Staff-Session`. Sessions are bound to that terminal. Guarded routes use the `staff` / `staff:owner,manager` middleware, after `ResolveTenant`. PIN guessing is locked out after 5 failures per staff member per terminal and 15 per terminal, for 15 minutes.
* Staff reach terminals through the sync feed (routed by `outlet_id`) **without** `pin_hash`. Never sync anything PIN-derived: the offline sign-in design is in `docs/offline-pin-signin.md` (proposal, awaiting decisions).
* Taking a device out of service (`App\Devices\DeviceLifecycle`, `POST /api/v1/devices/{id}/unpair` by owner/manager, or `php artisan pos:unpair`):
  * **retire** (replacing a device): it may still push mutations made *before* the cutoff for 72 h (later ones are rejected `device_retired`); everything else gets `403 device_retiring`. It becomes revoked when it calls `devices/retired` or the grace period ends.
  * **revoke** (lost / stolen): everything gets `403 {"error":"device_revoked","wipe":bool}` at once. With `wipe` the device erases its data and calls `devices/wipe-confirm`; only then are its tokens deleted (a deleted token would leave it unable to learn it should wipe). Unsynced sales on a wiped device are lost — `GET /api/v1/devices` shows each device's `outbox_pending` as of its last push.
  * `EnsureDeviceActive` runs on every device route after `ResolveTenant`. Re-pairing returns a device to `active`.

### Sync mutations

| Type | Fact written | Flags (never rejections) |
|---|---|---|
| `order.create` | order, items, payments, `sale` movements | `price_mismatch`, `product_deleted`, `negative_stock`, `offline_noncash_payment`, `unknown_staff` |
| `order.void` | `order_voids` row, `void` movements returning the stock, negative `reversed` payments; `orders.status = 'void'` is a projection | `unauthorized_void` (not owner/manager), `duplicate_void` (second void is a no-op) |
| `payment.add` | payment; order becomes `paid` once covered | `overpaid`, `payment_on_void_order`, `offline_noncash_payment` |
| `stock.adjust` | one signed movement (`waste`, `adjust`, `transfer_in`, `transfer_out`); never an absolute count | `unauthorized_adjustment` (non-waste by non-manager), `negative_stock`, `product_deleted` |
| `session.end` | `time_sessions` row with the terminal's charge **and** `server_amount_sen` from `TimeBilling` | `session_amount_mismatch` |

All stock changes go through `App\Sync\StockLedger::move()`; order lookups through `App\Sync\Facts::order()` (partition-pruned, locked).

Postgres role `allurus_app` (non-superuser, `NOBYPASSRLS`, so RLS is really exercised) owns:

* `allurus` — dev (`.env`)
* `allurus_test` — Pest (`phpunit.xml`)
* `allurus_sim` — simulator; `sim:run` runs `migrate:fresh` on it every time. Never point it elsewhere.

## Conventions

* Tests first for anything touching money, tax, tenancy or sync. Use Pest.
* Tenant isolation test for every new tenant table: two tenants, assert neither can read or write the other's rows, including via raw queries (RLS).
* Every new sync mutation type gets a simulator scenario as well as Pest tests.
* API: versioned under `/api/v1`, API Resources, cursor pagination, `Idempotency-Key` on non-sync POSTs.
* Queue jobs carry `tenant_id` and call `TenantContext::set()` first.
* Demo data uses `DemoSeeder` only. Demo staff PINs are 1111 / 2222 / 3333.
* Windows PowerShell 5 writes a UTF-8 BOM with `Set-Content -Encoding utf8`, which breaks PHP namespaces. Edit files with editor tools, not PowerShell.

Known gaps:

* Refunds (partial, by line) aren't a mutation yet; only whole-order voids. Same pattern: new rows, negative payments, `refund` movements.
* Stocktake (an absolute count) isn't supported: it must become a delta computed on the server against the ledger at the count's time.
* Sessions are only synced when they end; a running session isn't visible to HQ or other terminals yet.
* A void or payment waiting on another terminal's order gives up after 72 h of *device* time; a badly skewed clock shifts that deadline.

* Offline PIN sign-in: proposal in `docs/offline-pin-signin.md` (recommended: per-device credential sealed by a hardware key, 6-digit manager PINs). Four decisions are open; nothing is built yet.
* A retiring device's cutoff uses its *device* clock, so a tampered clock could backdate sales. That's why lost/stolen devices are revoked, never retired.
* `order.create` doesn't yet check that `staff_id` is a real, active staff member of the tenant (it should flag a conflict, never reject a sale).
* No HQ users yet: pairing codes come from the CLI or from an owner/manager on an already-paired terminal. The first device per tenant needs the CLI.

* The server doesn't recompute or check terminal pricing against `PricingEngine` yet (it should flag, never rewrite — rule 4). The payload doesn't yet carry the full engine input (line discounts, order discount, service-charge policy) needed to do that.
* Modifiers aren't priced in the simulator yet (the engine supports them; the local catalogue doesn't map them to lines).
* `tax_rules` aren't in the sync feed yet (the trigger needs a tenant; national rules need their own pull path).
* The server doesn't yet flag terminals with skewed clocks (the simulator only reports the skew).
* Demo tax rates are illustrative. Confirm with RMCD before go-live.
